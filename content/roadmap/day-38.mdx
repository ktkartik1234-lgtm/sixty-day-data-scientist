Yesterday you built semantic search; today you wire it to a generator so the
model answers from *your* documents. RAG is the highest-leverage GenAI
architecture for knowledge work — and it is two components you already own.

## Pipeline anatomy: chunk, embed, retrieve, generate

```python
def answer(question: str, index, llm, k=3) -> str:
    hits = index.search(question, k=k)                 # 1. retrieve
    context = "\n\n".join(f"[{i}] {doc}" for i, (doc, _) in enumerate(hits))
    prompt = f"""Answer using ONLY the sources below. Cite them as [n].
If the sources do not contain the answer, say you don't know.

Sources:
{context}

Question: {question}"""
    return llm(prompt, temperature=0.0)                # 2. generate, grounded
```

Everything upstream of the prompt is Day 37 (chunking, embeddings, search);
everything inside it is Day 35 (grounding, structure). RAG is composition,
not novelty.

## Why retrieval beats fine-tuning for knowledge

- **Freshness** — a fine-tune is frozen at training time; an index is
  re-built in minutes whenever documents change.
- **Provenance** — RAG can cite the chunk it used; fine-tuned weights cannot
  show their work, so wrong facts are undebuggable.
- **Scope** — swap the index per customer or tenant; the model stays put.
- **Division of labor** — prompting or fine-tuning teaches *behavior*
  (format, tone, skill); retrieval supplies *knowledge*. Day 39 turns this
  into a decision framework.

## Reranking: retrieve wide, read narrow

Embedding models score query and document independently (bi-encoders) —
fast, but coarse. A cross-encoder reads query and document *together* —
accurate, but it needs a forward pass per candidate. So do both:

```python
import numpy as np

def rerank(query, candidates, cross_encoder, k=3):
    pairs = [(query, doc) for doc, _ in candidates]   # 50 candidates
    scores = cross_encoder.predict(pairs)             # expensive, precise
    top = np.argsort(-scores)[:k]
    return [candidates[i] for i in top]
```

Retrieve 50 with the bi-encoder, rerank down to 3–5 with the cross-encoder.
This two-stage pattern shows up everywhere in information retrieval.

## Grounding, citations and refusal

The prompt contract has three clauses: answer only from sources, cite every
claim as [n], and refuse when the sources are silent. Then *verify
programmatically* — a citation is valid only if it points at a chunk that
was actually retrieved:

```python
import re

def check_citations(out: str, n_retrieved: int) -> bool:
    cited = {int(m) for m in re.findall(r"\[(\d+)\]", out)}
    return 0 < len(cited) and cited.issubset(set(range(n_retrieved)))
```

## Evaluation: hits@k on the retrieval layer

Score retrieval before you score answers. With a gold document per question:

$$\text{hits@}k = \frac{1}{|Q|} \sum_{q \in Q} \mathbf{1}\left[ \text{gold}(q) \in \text{top}_k(q) \right]$$

```python
def hits_at_k(gold: dict, search, k: int = 3) -> float:
    hits = sum(
        1 for q, doc_id in gold.items()
        if doc_id in {i for i, _ in search(q, k)}
    )
    return hits / len(gold)
```

Report hits@1, hits@3, hits@5 separately from answer quality: retrieval and
generation fail for different reasons and are fixed with different knobs.

<Callout kind="warn" title="Most LLM bugs are retrieval bugs">
  When the right chunk never reaches the prompt, no prompt rewrite or bigger
  model can save the answer. If your bot is wrong, check hits@k first and fix
  chunk size, overlap or the embedding model before touching the generation
  prompt. Teams burn weeks tuning prompts to compensate for a retrieval
  layer that was quietly broken.
</Callout>
