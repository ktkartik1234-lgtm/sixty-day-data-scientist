Days 23 and 24 built a network and its gradients in bare NumPy. PyTorch's
pitch is simple: keep the NumPy habits, automate the backward pass, and borrow
a GPU while you are at it. Every remaining day of this phase assumes today's
vocabulary.

## Tensors: NumPy that can move to the GPU

```python
import torch

a = torch.arange(6, dtype=torch.float32).reshape(2, 3)
b = torch.ones(3, 2)
print((a @ b).shape)            # torch.Size([2, 2]) — same matmul as NumPy
print(a.sum(), a[1, :2], a.T)   # reductions, indexing, transpose: all familiar

n = torch.from_numpy(a.numpy())         # zero-copy bridge when dtypes allow
w = torch.randn(3, 3, device="cpu")     # the one new idea: where a tensor lives
print(w.device)
```

The API is deliberately NumPy-shaped — same broadcasting, same slicing, same
reductions. The deltas are the device and what comes next.

## Autograd: the chain rule as a service

```python
x = torch.randn(4, 3)
W = torch.randn(3, 2, requires_grad=True)   # track this leaf
y_hat = (x @ W).tanh()
loss = y_hat.square().mean()

loss.backward()                # Day 24's reverse pass, automated
print(W.grad.shape)            # (3, 2) — d loss / d W, same shape as W
print(x.grad)                  # None — x never asked to be tracked
```

During the forward pass, every operation on a tracked tensor appends a node to
a graph. `.backward()` walks that graph in reverse and deposits gradients in
each leaf's `.grad`. Two habits to internalize now: gradients **accumulate**
across calls until you zero them, and the graph is freed after `.backward()`
— recompute the forward pass if you need to differentiate again.

## nn.Module: models as objects

```python
import torch.nn as nn

class MLP(nn.Module):
    def __init__(self, d_in, h, d_out):
        super().__init__()
        self.body = nn.Sequential(
            nn.Linear(d_in, h), nn.ReLU(), nn.Linear(h, d_out)
        )

    def forward(self, x):
        return self.body(x)

model = MLP(3, 16, 2)
print(sum(p.numel() for p in model.parameters()))   # 98 = 3*16+16 + 16*2+2
```

`nn.Linear` is Day 23's `X @ W + b`; a module is a named container of tensors
that know they are parameters. `.parameters()` is the handle the optimizer
subscribes to, and `numel` counting is how you sanity-check architectures.

## Device placement and the first training step

```python
device = "cuda" if torch.cuda.is_available() else "cpu"
model = MLP(3, 16, 2).to(device)
xb = torch.randn(8, 3, device=device)
yb = torch.randn(8, 2, device=device)

out = model(xb)
loss = (out - yb).square().mean()
loss.backward()
with torch.no_grad():                       # the update is not part of the graph
    for p in model.parameters():
        p -= 0.1 * p.grad
model.zero_grad(set_to_none=True)
```

Model and batch must live on the same device, and the gradient update runs
under `no_grad` because it is bookkeeping, not a differentiable operation.
Tomorrow this step gets wrapped in a real loop with a real optimizer.

<Callout kind="warn" title="The two first-week bugs">
Forgetting `.to(device)` on either the model or the batch raises a device
mismatch error — loud, so you will fix it fast. Far sneakier: forgetting to
zero gradients. They accumulate, every step becomes far too large, and
training diverges with no error message anywhere. Calling `zero_grad()` before
every `.backward()` is muscle memory from today onward.
</Callout>
